# 迅雷 AI 片库：技术选型与开源复用计划

> 首次调研：2026-07-28  
> 字幕时间轴补充调研：2026-08-08

## 1. 结论先行

不建议从零实现视频转写、场景检测、播放器、向量检索等通用能力，也不建议直接 Fork 某个端到端“视频 AI”项目改造成迅雷产品。

更稳妥的方案是：

1. 产品界面和业务流程根据迅雷场景重新设计。
2. 底层能力组合成熟、许可证友好的开源组件。
3. 端到端项目只复用架构思路和少量独立服务代码。
4. Demo 阶段使用预生成索引和确定性数据，保证演示稳定。
5. 生产化方案保留真实 ASR、混合检索和多模态理解的可替换接口。

推荐组合：

```text
媒体处理：FFmpeg
语音转写：FunASR / faster-whisper
精确时间戳：stable-ts（已接入）/ WhisperX（更重的第二级方案）
镜头候选：PySceneDetect
中文语义检索：FlagEmbedding / BGE-M3
结构化与向量存储：PostgreSQL + pgvector
检索流程参考：YT-Navigator
网页播放器：Plyr
多模态补充：Qwen3-VL 或商业视频理解 API
```

## 3. 候选项目评估

Star 数为 2026-07-28 调研时的 GitHub 数据，仅用于判断社区成熟度。

### 3.1 建议直接复用

|---|---:|---|---|---|
| [faster-whisper](https://github.com/SYSTRAN/faster-whisper) | 24.6k | MIT | 视频音频转写、批处理、量化推理 | 生产链路首选 ASR |
| [stable-ts](https://github.com/jianfch/stable-ts) | 2.2k | MIT | 根据波形静音区收紧词级时间戳、按语音间隔重组 | 精准模式时间轴后处理，已接入 |
| [WhisperX](https://github.com/m-bain/whisperX) | 23.3k | BSD-2-Clause | 词级时间戳、VAD、说话人分离 | 需要精确跳转时按需增加 |
| [PySceneDetect](https://github.com/Breakthrough/PySceneDetect) | 5.1k | BSD-3-Clause | 切镜、渐变和场景候选检测 | 作为章节候选信号，不直接等同于章节 |
| [FlagEmbedding](https://github.com/FlagOpen/FlagEmbedding) | 12.0k | MIT | BGE-M3 中文/多语言向量、稀疏检索和重排 | 中文语义检索首选 |
| [pgvector](https://github.com/pgvector/pgvector) | 22.4k | PostgreSQL License | 在 PostgreSQL 中存储和查询向量 | 首版生产架构优先 |
| [Plyr](https://github.com/sampotts/plyr) | 29.9k | MIT | 网页播放器、字幕、键盘和移动端控制 | Demo 播放器首选 |
| [FFmpeg](https://github.com/FFmpeg/FFmpeg) | 62.5k | LGPL/GPL 取决于构建 | 提取音频、关键帧、转码和媒体信息 | 后端媒体处理标准组件 |

直接复用的原因：

- 都是边界清晰的基础组件，不会绑死产品架构。
- 维护活跃，文档和社区问题较充分。
- 除 FFmpeg 构建需单独核对外，许可证适合在项目中作为依赖使用。
- 能覆盖最难、最不值得自研的通用能力。

### 3.2 建议复用架构与部分代码

#### YT-Navigator

- 仓库：[wassim249/YT-Navigator](https://github.com/wassim249/YT-Navigator)
- Star：601
- 许可证：MIT
- 技术栈：Django、PostgreSQL、PGVector、Sentence Transformers、BM25、Cross Encoder、LangGraph。

它与本方案最接近，已经实现：

- 视频元数据与字幕分开入库。
- 字幕按时间切块并生成向量。
- 语义检索与 BM25 关键词检索并行。
- 合并、去重和 Cross Encoder 重排。
- 搜索结果返回视频、字幕片段和精确时间点。
- 问答只在需要时调用检索工具。

值得复用：

- 数据模型：`Video`、`VideoChunk`、时间戳片段。
- “语义召回 + BM25 + 重排”的混合检索流程。
- 搜索结果按视频聚合并保留命中片段的思路。
- 无相关证据时拦截问答的路由逻辑。

不建议整仓 Fork：

- 项目围绕 YouTube 频道和英文内容设计。
- 默认模型 `bge-small-en-v1.5` 不适合中文片库。
- Django 页面与迅雷影音的产品形态差异较大。
- 登录、频道扫描和 YouTube 抓取模块对本项目无用。

结论：参考服务层和检索算法，按迅雷的数据模型重新实现；如直接借用独立代码段，保留 MIT 版权声明。

### 3.3 只建议借鉴，不直接复制代码

| 项目 | Star | 许可证/限制 | 借鉴内容 | 不直接复用原因 |
|---|---:|---|---|---|
| [Immich](https://github.com/immich-app/immich) | 109.1k | AGPL-3.0 | 混合搜索界面、后台索引任务、传统搜索与智能搜索并存 | AGPL 传染性强，系统体量过大 |
| [Jellyfin](https://github.com/jellyfin/jellyfin) | 55.1k | GPL-2.0 | 片库信息架构、季集组织、播放与续播 | 不是 AI 搜索系统，GPL 代码不适合直接并入 |
| [MoviePilot](https://github.com/jxxghp/MoviePilot) | 11.4k | GPL-3.0，README 另有使用声明 | 媒体命名识别、刮削、整理、插件边界 | 产品和合规边界复杂，不复制代码 |
| [NVIDIA VSS](https://github.com/NVIDIA-AI-Blueprints/video-search-and-summarization) | 1.8k | 多份许可证 | 长视频分块、稠密描述、视频搜索、问答和片段召回架构 | 依赖 NVIDIA NIM 和较重 GPU 基础设施 |
| [Qwen3-VL](https://github.com/QwenLM/Qwen3-VL) | 19.7k | Apache-2.0 | 无对白内容理解、关键帧描述、时间定位 | 模型和推理资源较重，Demo 不应强依赖 |
| [Qdrant](https://github.com/qdrant/qdrant) | 33.6k | Apache-2.0 | 大规模向量检索 | 首版使用 pgvector 已足够，避免多维护一个服务 |

值得吸收的设计：

- Immich：经典文件名搜索与 AI 语义搜索同时存在，允许按人、时间、类型和文件路径筛选。其智能搜索使用 PostgreSQL 和 CLIP 向量，不强迫所有搜索走大模型。
- MoviePilot：媒体识别、整理、刮削和媒体库刷新应是解耦步骤；错误结果需要人工确认。
- NVIDIA VSS：长视频不一次性送入模型，而是分块生成稠密描述，再做聚合摘要和片段召回。
- Jellyfin：片库、剧集、季集、续播和播放器应保持可扫描的传统媒体产品结构。

### 3.4 不建议采用

- 搜索结果中大量低 Star、单次提交的“AI Video Summarizer”“Video RAG”学生项目。
- 仅用 LangChain 拼接“转写 + 向量库 + 聊天框”的仓库。
- 没有许可证或许可证不清晰的仓库。
- 强依赖某个收费向量数据库、单一模型 API 或 YouTube 字幕接口的端到端项目。
- 把每个镜头切换直接当作一个章节的实现。

这些项目可以帮助理解最小流程，但不适合作为提交作品的底座。

### 3.5 未采用：七牛云实训营实时字幕项目

补充调研了 `xiaoxiaomoyu/moyu-flowsub` 与 `PPBrook/VoiceBridgeAI`。二者 Star 很少，不能作为
核心算法成熟度证据；同时它们面向实时字幕/同声传译，不符合当前“上传后整理片库”的主要体验。
因此本项目当前不采用七牛云实时字幕链路，也不在播放器中展示其实时状态协议。

当前迅雷 AI 片库处理的是已上传视频，优先保证离线字幕精轴。产品实现只保留“小红书烤肉/对轴”
方法对本项目有价值的部分：先由 ASR 给出词轴，再用真实停顿、标点和显示长度约束做后台对轴，
最后由 MiniMax-M3 做低置信文本校订。该策略不作为独立 Tab 暴露给用户，评委看到的是已整理
完成的字幕、章节和问答结果。

## 4. 推荐技术架构

### 4.1 Demo 架构

Demo 的目标是让评委完整体验产品闭环，不是现场跑完长视频 AI 计算。

```text
React + TypeScript + Vite
        ↓
本地演示数据与预生成视频索引
        ↓
确定性的搜索、摘要、章节和问答响应
        ↓
Plyr 播放器 + 自定义章节侧栏
        ↓
点击时间点跳转真实视频
```

Demo 中可以真实实现：

- 搜索框、筛选和结果排序。
- 关键词与预设语义标签的混合匹配。
- 搜索结果匹配原因。
- 片库、视频详情、摘要和章节。
- 视频播放器时间点跳转。
- 预设问题的证据回答和片段跳转。
- AI 索引进度、纠错和防剧透状态。

Demo 中不现场执行：

- Whisper 长视频转写。
- BGE 模型推理。
- 大规模向量数据库。
- Qwen3-VL 或 Gemini 长视频分析。

这样做不是伪造技术，而是把已验证可行的后台链路预计算，保证评审环境无需 GPU、API Key 和长时间等待。

### 4.2 生产化架构

```text
迅雷云盘文件
   ├─ FFprobe：媒体元数据
   ├─ 现有字幕：直接读取
   ├─ 无字幕：faster-whisper
   ├─ 精确对齐：stable-ts 波形静音抑制；WhisperX 按需升级
   ├─ 镜头候选：PySceneDetect
   └─ 按需视觉理解：Qwen3-VL / 视频理解 API
                ↓
        结构化视频与时间片段
                ↓
 PostgreSQL 元数据 + pgvector 向量
                ↓
 BM25/全文检索 + BGE-M3 语义召回
                ↓
 合并去重 + BGE Reranker
                ↓
 视频结果 / 章节 / 问答依据 / 时间跳转
```

### 4.3 为什么首选 PostgreSQL + pgvector

- 片库业务本身有大量结构化条件：文件名、目录、季集、年份、演员、观看进度。
- 向量只负责语义召回，不能取代关系型数据。
- YT-Navigator 已验证元数据和向量放在 PostgreSQL/PGVector 中的简洁性。
- Demo 后若做小规模真实后端，可以在一个数据库中完成，不必增加 Qdrant 运维。
- 当视频规模和召回吞吐明显扩大后，再评估独立向量数据库。

### 4.4 为什么中文检索选 BGE-M3

FlagEmbedding 的 BGE-M3 支持：

- 100 多种语言。
- 最长 8192 token 输入。
- Dense、Lexical 和 Multi-vector 三种检索方式。
- 中文与跨语言查询。

相比 YT-Navigator 默认的英文向量模型，它更适合“刘德华演的警匪片”“讲 Cookie 登录的 Python 教程”等中文自然语言查询。

## 6. 实施计划

### 阶段一：交互 Demo 骨架

目标：先打通最重要的用户闭环。

- 建立 React + TypeScript + Vite 项目。
- 使用 Plyr 构建真实视频播放器。
- 建立片库、搜索结果、视频详情和播放器四个核心视图。
- 从现有产品方案提取演示文案和功能标签。
- 使用 Lucide 图标，不自行绘制基础图标。

验收：

- 桌面和移动端布局均无重叠。
- 搜索、进入详情、播放、章节跳转均可操作。
- 不依赖登录、GPU 或 API Key。

### 阶段二：产品闭环

目标：让 AI 能力通过可验证交互表现出来。

- 准备 8 至 12 个结构混乱的云盘视频样本。
- 支持自然语言搜索和传统精确搜索。
- 每条结果展示匹配原因和置信度。
- 详情页展示摘要、标签、季集、重复版本和智能章节。
- 问视频返回引用片段并跳转。
- 增加无结果、低置信度、索引中和识别错误状态。

验收：

- 至少 5 个预设自然语言查询得到合理结果。
- 问答不能脱离视频证据。
- 每个时间点都能真实控制播放器跳转。

### 阶段三：真实技术样例

目标：证明方案不是纯 UI 概念。

- 选取一个短视频，离线运行 faster-whisper。
- 使用 PySceneDetect 生成镜头候选。
- 用 BGE-M3 对字幕片段生成向量。
- 产出一份真实的字幕、章节候选和语义检索结果。
- 将生成结果导入 Demo 数据。

验收：

- 仓库保留可重复执行的数据处理脚本。
- Demo 中至少一个视频的数据来自真实处理链路。
- 处理脚本与前端数据结构一致。

### 阶段四：提交与录屏

- 部署静态 Demo，生成公开链接。
- 补充第三方组件声明。
- 用 Playwright 检查桌面与移动端。
- 录制完整用户路径：海量片库 → 一句话搜索 → 匹配原因 → 摘要与章节 → 问视频 → 时间点跳转。
- 将 Demo 链接、PDF 和录屏汇总到统一提交目录。

## 8. 开始开发前的最终选择

建议按以下边界启动：

- 前端：React + TypeScript + Vite。
- 播放器：Plyr。
- 图标：Lucide。
- Demo 数据：预生成 JSON。
- 真实样例：faster-whisper + PySceneDetect + BGE-M3。
- 检索架构：参考 YT-Navigator 的 BM25 + 向量召回 + 重排。
- 生产存储：PostgreSQL + pgvector，仅写入架构说明，Demo 不强行部署数据库。
- 多模态模型：保持接口层，不在首版绑定 NVIDIA VSS 或本地 Qwen3-VL。
- GPL/AGPL 项目：只借鉴，不复制代码。

这套组合既避免从头造轮子，也避免被某个体量过大或许可证复杂的项目绑住。
